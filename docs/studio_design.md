# Astrion Studio / Design 产品设计草案

> 日期：2026-10-27
> 状态：当前讨论归档，尚未进入实现；本次授权范围为保存文档与项目记忆。
> 用途：保存已表达的产品方向、当前建议和待定问题，作为后续讨论与技术设计的起点。
> 注意：下文明确区分用户方向与方案建议；记录方案不等于所有细节已经定稿，也不代表相关能力已经实现。

## 1. 产品背景与已明确的方向

Astrion 当前有两种模式：

- **Agent**：全功能智能体，围绕任务和工作区规划、执行、验证并交付结果。
- **Chat**：轻量智能体，不要求工作区或执行环境，主要用于交流、学习和探索。

用户当前最想增加的是 **Astrion Design**：专门制作产品／网页原型，参考 Claude Design，并重视类似 Codex 浏览器的可视化反馈方式。

用户明确看重：

1. 网页作品本身具有较强的交互性和可操作性。
2. 可以更轻松地框选元素或区域。
3. 可以针对选中内容批注，并把意见与相关上下文发送给模型修改。

**Studio 作为上层工作台、Design 作为其中一种作品类型／工作方式，是当前讨论方案，具体命名与入口组织尚未定案。**

### 1.1 其他方向的定位

- **Knowledge**：用户早已考虑的品类，核心是「智能体辅助管理的个人知识库」。用户持续关注 NotebookLM 和 Open WebUI；主要难点为知识管理、图片／视频／Word／PPT／Excel 等多模态与非 UTF-8 文件的解析和归类，以及 RAG 引入的复杂度、性能与运维成本。保留为长期方向，本草案不展开其实现。
- **Automate**：用户认为与现有 Agent 功能过于重合，不值得另加一个新功能。不将其列为本次新增模式的优先方向。

## 2. Studio 的建议定位

**与智能体一起制作、试用和修改交互作品的工作台。**

- 对话用于表达意图、讨论方案和发起修改。
- 作品是主要操作对象，具有独立身份、预览入口和版本。
- 用户围绕作品试用、选择、批注、比较与继续修改。
- 共用现有智能体基础能力，避免为 Studio 复制整套模型／工具循环。

与 Agent 的建议区别在主要交互方式：Agent 围绕任务、工作区及执行结果；Studio 围绕正在创作的作品。两者的工具和基础机制可以复用。

### 2.1 对早期 Artifacts 的参考范围

借鉴早期 Artifacts「对话旁的独立作品」：查看、运行并持续迭代同一件作品。

当前 Artifacts 已扩展到多人协作、持久数据、外部工具连接和内嵌 AI。不能把这些新能力自动视为 Astrion Studio 的首版范围，也不要求完整复刻其产品。

## 3. 作品类型与扩展顺序建议

初期围绕 HTML／CSS／JavaScript／SVG 网页作品建设共用底座。作品可以由多个文件组成，不要求单文件 HTML，也不预先承诺任意框架或项目都能无配置运行。

| 作品类型 | 用途示例 | 建议顺序 | 额外复杂度与边界 |
| --- | --- | --- | --- |
| **Design：产品／网页原型** | 页面设计、组件状态、多页面流程、可点击产品原型 | 核心场景 | 重点建设预览、选中、区域框选、批注与模型修改 |
| **交互小工具** | 报价计算器、方案评分器、排期工具、文本转换器 | 首版可覆盖的用途 | 以浏览器内可完成、自包含为主；账号、支付、数据库及外部授权另行评估 |
| **交互讲解与模拟** | 算法分步演示、参数模拟、产品逻辑解释、教学图解 | 首版可覆盖的用途 | 优先 HTML／SVG；复杂模拟及 Canvas／WebGL 对象选择会增加成本 |
| **网页演示与可视化报告** | 产品提案、翻页演示、交互报告、可筛选图表 | 后续扩展 | 补充分页、演示与导出体验；不等同于 PPT 编辑 |
| **图解与流程表达** | 用户流程、结构图、时间线、信息图 | 后续扩展 | 先考虑模型生成与批注修改；任意拖拽节点、连线和自动布局属于更大的编辑器工程 |

表中的复杂度为讨论阶段的工程判断，指在共用底座已建立后的增量成本，不代表实现 Studio 本身简单，也不构成交付承诺。

### 3.1 建议的入口组织

- 若采用 Studio 名称，以一个工作台承载上述作品类型。
- 不为每个用途立即新增独立顶层模式，可在新建作品时提供类型或起点。
- Design 为重点入口；其他类型共用作品、预览、批注和版本机制。
- 仅当实际使用证明某品类需要独立操作流程时，再讨论拆分。

## 4. 核心交互链路

**试用作品 → 切到批注 → 选中元素或框选区域 → 编写多条意见 → 一次发送 → 查看新版本。**

### 4.1 试用与批注

- 运行／试用时允许用户正常操作原型。
- 批注时支持选中元素及区域框选，避免与页面点击、拖动等行为互相干扰。
- 支持对多个位置分别添加意见，汇总后一次发送。
- 批注既能表达局部外观修改，也能表达交互和内容问题。
- 元素多选、框选命中规则、嵌套元素层级选择及跨页面批注的具体行为待设计。

### 4.2 发给模型的建议上下文

不能只传一句批注或一张截图。建议组合：

- 作品身份与版本；
- 页面／路由和视口尺寸；
- 选中的元素或区域及其位置；
- 必要的邻近内容与相关 DOM 信息；
- 当前可见状态和对应截图；
- 用户逐条批注及其与选中对象的关联。

只取修改所需的上下文，避免无差别发送完整页面和大量无关数据。具体字段、大小限制、截图方式与传输协议待技术设计。

### 4.3 元素定位与源码修改

- 对 Studio 自己生成的作品，可评估稳定元素标识，辅助模型定位。
- DOM 选中不等于已解决源码定位，尤其是 React／Vue 的组件复用、条件渲染、动态列表和样式来源。
- 任意现有项目的 DOM 到组件源码映射能力需要单独评估，不作为当前已实现能力。
- Canvas／WebGL 的内部对象不天然具有 DOM 元素边界，不能承诺直接沿用普通元素选择。

### 4.4 批注绑定版本

- 批注绑定提出意见时的作品版本、页面及目标对象。
- 新版本可能移动或删除目标，不能把旧选择器无条件应用到新版本。
- 用户应能回到旧版本查看原批注；跨版本继续应用时需要核对对象。
- 批注完成、失效、保留及重新定位的状态规则尚未定稿。

### 4.5 批注修改与直接编辑的分期建议

首版建议优先实现「框选／选中 → 批注 → 模型修改」。

直接拖动布局、属性面板改样式、直接编辑文字后可靠写回源代码，需要处理布局约束、样式来源、撤销和代码往返一致性。建议后续单独评估，不将其等同于已具备的批注能力。

用户当前明确强调框选、批注和发送给模型；完整可视化建站编辑器并非已确认的首版要求。

## 5. 作品与版本管理建议

作品应能独立于聊天被找到、打开并继续修改，同时保留与生成／修改对话的关联。

建议的概念对象：

- **作品**：名称、类型、关联对话和当前版本。
- **页面／文件**：作品包含的页面、源码、样式、脚本及资源。
- **版本**：可回看、可预览的作品快照。
- **批注**：绑定版本、页面和目标对象的意见。

以上只是概念边界，不指定数据库表、磁盘目录、ID 格式、API 或存储引擎。

需进一步讨论：

- 每次模型修改何时形成一个版本；
- 生成失败或中断时如何保留上一可用版本；
- 回看、恢复和分叉的关系；
- 单一作品与多个对话之间的关联；
- 多页面和多文件快照的一致性。

### 5.1 小工具的运行数据

作品版本与用户输入／运行数据是不同对象。

「工具能运行」不自动意味着「输入长期保存」。若支持持久化，必须另行确定作品归属、版本升级后的保留或迁移、导出后的行为，以及数据与作品源码的分离方式。当前不默认承诺持久数据、多人协作或后台服务。

## 6. 当前 Astrion 基础与技术边界

以下是 2026-10-27 本次代码阅读的有限结论，实施前仍需核对最新代码，不等同于 Studio 已实现。

| 现有位置 | 已观察到的基础 | 与 Studio 的关系 |
| --- | --- | --- |
| `static/src/components/chat/quickdock/PreviewPanel.vue` | iframe 页面预览、刷新、面板宽度调整等 | 可参考或复用部分预览界面机制 |
| `static/src/stores/preview.ts` | 预览目标、运行时信息与地址推导 | 现有预览管理基础，不是完整作品管理 |
| `static/src/utils/showHtmlSandbox.ts` | HTML 沙箱、CSP 与相关守卫 | 可参考隔离渲染机制，具体能力需重新匹配需求 |
| `static/src/utils/showHtmlFullscreen.ts` | HTML 全屏预览及生命周期管理 | 可参考或复用部分展示能力 |
| `modules/preview_targets.py` | HTML／localhost 目标记录与启用边界 | 当前文件／服务预览仅在 host 模式启用 |

本次检查的预览组件与 store 主要是页面查看器，未形成本文提出的元素选择、区域框选、批注及作品版本链路。此判断限于本次检查范围，不据此声称仓库内没有任何其他相关实验。

若 Studio 同时面向网页部署与桌面端，必须单独设计作品运行和预览服务，不能直接把当前 host 预览入口照搬到云端。

## 7. 建议的首版范围

> 本节保存当前推荐方案，尚未形成实施计划或逐项验收契约。

1. **核心场景**：产品／网页原型 Design。
2. **顺带覆盖的用途**：自包含交互小工具、HTML／SVG 交互讲解。
3. **关键操作**：试用与批注切换、元素选择与区域框选、多条意见批量发送。
4. **作品管理**：独立作品入口、页面／文件、版本快照与继续修改。
5. **后续扩展**：网页演示、图解、轻量直接编辑。

当前未将完整 Office 编辑、多用户实时协作、外部工具授权、任意应用后端、复杂视频编辑、任意代码项目的无配置运行列为首版默认范围。

## 8. 后续需要拍板的问题

- 对外名称采用 Astrion Design，还是 Astrion Studio 下以 Design 为重点？
- Studio 是否独立顶层模式，以及与 Agent 的进入、交接和返回方式。
- 是否需要用户选择工作区，作品资源如何装配，支持哪些部署形态。
- 首版作品技术栈与依赖边界，静态作品和需要构建／开发服务器的项目如何处理。
- 页面／画板的组织方式，是否需要多方案并排、缩放和平移。
- 选择、框选、截图、DOM 信息与源码映射的协议。
- 版本生成、失败恢复、回看与继续编辑规则。
- 导出格式、资源打包和导出后的运行承诺。
- 小工具是否保存运行数据；如支持，数据生命周期如何定义。
