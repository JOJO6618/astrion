# Astrion Docker 版独立 fork 方案

调研基线为 `20da725b7f0a20917579511efac96901d2a8d9f5`。本文记录产品归属、完整拆分的依赖和验收条件。

## 首轮范围（2026-11-21）

首轮聚焦主仓 Host Web、CLI/headless 和桌面端。任务工作树 `refactor/host-only-main` 从 `main` 的 `172396f657e3099767cceffa82c637dda8f90421` 建立。该提交保留双模式、Docker 镜像配置、Android 工程与普通／API 用户端点，可作为后续建立 Docker fork 的源码候选。实际部署的版本、镜像和数据口径另行核验。

下文阶段 0 至 4 描述两边正式切换的完整流程。首轮落实主仓解耦及裁剪，Docker fork 的建立、数据接管、Android 发布与现网切换需另行决策。仓库内未发现旧 Docker 部署自动跟随 `main` 的配置。发布前需在实际环境核对运行版本及更新方式，并为在用部署固定可恢复版本。

- full 与 headless 通过独立装配测试，覆盖 Host 浏览器登录与附件、CLI Bearer 会话、模型目录和旧配置在数据初始化前拒绝。Host 密码保护 27 项、定时任务 215 项、Git 工作树 54 项通过。

- 合并前的 macOS ARM64 无签名目录包通过包内 Python、Host Web 与 headless、登录页 HTTP 200、8 个前端构建入口和 Quick Chat 辅助程序检查。

## 1. 产品归属与影响判断

| 主仓 `main` | Docker fork |
| --- | --- |
| macOS / Windows 桌面端、Quick Chat、桌面更新、独立浏览器 | 面向多人部署的 Web 服务、普通账号、邀请码、租户管理、用户配额、容器项目 |
| Host 浏览器界面、可选 Host 密码、本机工作区和 Host 原生沙箱 | Docker 镜像和工具环境、容器生命周期、容器资源额度、只读与子智能体隔离、容器专用项目记忆挂载 |
| 本机 CLI、`server.headless_app`、Host Gateway Bearer 和 Host 工作区接口 | API 用户、API Token、API 用户工作区与独立用量、管理入口和多用户 `/api/v1` 接口 |
| Host Web 的窄屏布局、浏览器上传下载、桌面原生文件操作 | Android 工程、Android 原生桥接、APK 检查与下载、发布和服务端版本元数据 |

两个仓库各自持有现有对话、任务、审批、工作流、定时任务及各自支持的工具能力。主仓保留 Host 本机 Gateway 和已有模型目录端点 `/api/v1/models`。两个仓库各自构建、发布和回归。第一版从同一个已知版本分叉，后续需要互相同步的修复按提交移植并分别验证。

**影响判断为高，风险集中在启动、身份、资源装配、执行隔离和历史数据。** 主仓目前实际执行 Host 命令时已经走原生路径。完成启动和资源分流后，现有对话、任务门闸、压缩、轮询、审批和持久化可以沿用。拆分过程中应保持 Host 数据路径、CLI 协议、浏览器认证和桌面桥接稳定，把内部模块移动与外部契约变更分开验证。

## 2. 拆分前耦合与主仓目标

| 边界 | 双模式基线的依赖 | 拆分后的行为 |
| --- | --- | --- |
| 服务启动 | [`server/state.py`](../server/state.py) 导入时实例化 `UserContainerManager`。桌面启动 full app，headless 又从 [`server/app_legacy.py`](../server/app_legacy.py) 导入初始化和后台启动函数，连带加载完整蓝图。 | full 与 headless 直接复用 Host 初始化、应用所需的认证注册和后台服务。保留首次默认工作区、Host Token 初始化、对话运行时回收和定时任务启动。Docker 容器回收由 fork 管理。 |
| 用户身份和工作区 | [`server/context/workspace.py`](../server/context/workspace.py) 解析 Host、普通用户和 API 用户三类作用域，随后由 [`server/context/resources.py`](../server/context/resources.py) 装配运行时。Host 登录和资源装配目前也经容器管理器领取 Host 句柄。 | 主仓通过已认证的 Host 身份和可信工作区目录解析资源，使用独立的 Host 资源生命周期。保留工作区和对话的实例键、装配锁、活动检查和清理。fork 分别验证普通和 API 用户的作用域。 |
| 执行与权限 | Host 和 Docker 共用 `LocalExecutionBackend`；文件、前后台命令和持久终端的上层模块有容器代理与只读 helper 的顶层导入。子智能体也从所属运行时装配资源。 | 共用执行契约继续作为 Host 工具入口。主仓各平台执行链直接绑定原生资源。Docker 的代理、只读、用户作用域和容器工具环境在 fork 守住原有隔离。 |
| 工作区首屏 | `/api/status` 的 `container.mode`、`/api/workspace-view` 的 `host_mode`、设置的 session 状态和本地缓存共同参与 Host 判定。模式影响 `/api/host/workspaces*` 与 `/api/projects*` 的选择。 | 前端工作区导航按可信的 Host 工作区快照装配，并保留零工作区、深链接、草稿和请求归属。状态接口在消费者迁移期间兼容旧字段。桌面壳和浏览器能力仍分别从各自环境判断。 |
| 模型与管理接口 | `/api/v1/models` 定义在 API 用户模块，桌面主界面和 Quick Chat 共用。`server/admin.py` 混有租户后台、Host 使用的策略、自定义工具、MCP 及重名文件路由。 | 抽出共用模型目录处理器，保留路径和响应字段。按实际调用保留 Host 所需权限与配置接口，租户管理交给 fork。附件路由各自保留一个明确的归属。 |
| Android 和发布 | APK 路由在 `server/status/app.py`，却从 `server/status/docker.py` 导入 Android 版本、APK 路径和更新说明辅助函数。APK 上传发布还有仓库外环节。 | fork 同时承担 Android 工程、桥接、端点和发布联动。主仓从状态蓝图解除 Android 导入，桌面更新继续使用自己的发布与官网契约。 |

`LINUX_SAFETY` 是需要单独处理的旧配置。当前启用后会阻止正常 Host 登录和本机 Gateway，同时可以让请求 Host 的资源装配尝试使用 Docker。主仓读取到旧的 `web`、`docker` 模式或启用的 `LINUX_SAFETY` 时，应在初始化身份和数据目录前明确指出需要切到 fork 或完成显式 Host 配置迁移。原生 Linux Host 沙箱仍按现行支持范围和失败策略运行。涉及路径授权、`sandbox` / `direct`、`readonly` / `plan` 与主子权限的边界见 [公共执行层](execution_contract.md)、[权限与沙箱](agents_details/permission_and_sandbox.md) 和 [Linux Host 沙箱](agents_details/linux_host_sandbox.md)。

## 3. 分阶段实施

### 阶段 0 · 固定基线与准备验收数据

- 核对实际要分叉的完整提交，以及现行 Docker 服务、Android 和桌面端实际发布版本。记录服务启动方式、镜像标识、状态读写目录、配置项来源、反向代理与 APK 发布入口。运行态凭证留在部署环境。
- 准备三组隔离数据。Host 全新数据，带多个工作区及 Chat／Agent 历史的 Host 升级数据，含普通账号、API 用户、Docker 容器项目和 Android 更新元数据的部署副本。保留一组从旧 Host 双读过 Web 账号的情况。
- 对基线记录关键行为与接口形状。包括 Host 登录、主应用和 Quick Chat 模型列表、工作区和草稿、活动对话恢复、命令取消、定时任务、文件显示，以及 Docker 用户与 API 用户工作区隔离。记录当期已知故障，供升级比较。

**完成条件**　确认分叉提交、部署切换对象、数据副本的可恢复性和回归入口。现网部署在后续切换阶段单独处理。

### 阶段 1 · 从基线建立可接管部署的 Docker fork

- 从同一已验证基线建立独立仓库，在副本中启动现有 Docker 模式。先验证普通用户和 API 用户签入、旧项目和文件、旧定时任务、运行历史、容器镜像和挂载、Android 更新和下载。
- 把普通用户和 API 用户身份隔离作为 fork 第一批验收项。当前 API Token 认证会写入浏览器 session 的部分字段，工作区解析又优先处理 Host 身份，源码能确认混合身份可能进入解析层。采用请求内、显式、互斥的 API 身份，在工作区解析、任务提交和文件访问处沿用认证所得的身份。验收检查 API 身份只得到其所属工作区。实际串用后果尚未实测。证据见 [`server/api_auth.py`](../server/api_auth.py)、[`server/context/workspace.py`](../server/context/workspace.py) 和 [`server/api_v1.py`](../server/api_v1.py)。
- 给 fork 准备独立配置与发布入口。保留镜像依赖、项目根和记忆挂载语义、容器限额、只读及子权限行为。切换部署目录时，查明容器名和项目标签的归属，避免旧实例仍运行时由新实例接管同名容器。
- 核对旧客户端使用的入口地址、证书、Cookie 配置和 API Token 验证所需的既有配置。凭证通过部署环境交接。明确既有 Web 会话是否允许重新登录，验证旧 API Token 按预期继续可用或已有明确的轮换安排。
- 把工程内 `android-webview-app/`、原生桥接、APK 路由及辅助函数和发布说明归到 fork。核对已发布 Android 包的 `HOME_URL` 仍能访问服务，保持现有下载和认证契约。私有上传流程由实际部署方接管，版本元数据和 APK 从同一发布批次同步。见 [Android 发布联动](agents_details/android_release.md)。

**完成条件**　fork 能用隔离副本独立构建和启动，旧普通账号、API 客户端和 Android 客户端的关键链路通过，且可恢复到基线服务。fork 不需要编译桌面目标才能发布 Docker Web 和 Android。借用基线启动的 Host 和桌面代码可在上述验证之后从 fork 裁剪。

### 阶段 2 · 从共用代码中接出主仓的 Host 路径

1. **启动与后台生命周期。** 从 full app 的模块级装配中提取 Host 共有的初始化。让 full/headless 各装配自己的路由，各自单独启动验证。保留首启默认工作区、Host Token、运行态日志、定时任务与对话终端回收。正式运行仍遵守同一数据根下 full 和 headless 的单进程约束。
2. **认证与工作区资源。** 给 Host 登录、Gateway 和后台触发器使用明确的 Host 身份。保留工作区授权、可信目录解析和读写分层。把登录和运行时取得的 Host 句柄从容器管理器中解出，使用现有运行时池和锁。迁移期间通过小的兼容层维持状态接口形状；状态查询保持轻量，缺少运行时仍可读已存历史和工作区。
3. **模型目录与 Host HTTP 契约。** full/headless 共用同一个模型目录处理器，保持 `/api/v1/models` 的 URL 与模型能力字段。保住 `/host-login`、会话状态、CSRF、Host 工作区、Gateway、任务与审批、文件、设置和提供商入口。处理 `auth`、`admin` 的重名 `/user_upload/` 与 `/workspace/` 注册，按可信工作区定位历史附件并保留路径校验。用现有桌面 Cookie 启动和前端资源读取验证。
4. **前端模式收口。** 先让工作区导航采用 Host 权威状态，包括零工作区、深链接、旧本地缓存、草稿作用域和切换期间请求归属。再移除 `/api/projects*` 消费者、Docker 文案及前端状态副本。在同一变更中核对主界面和设置页的初始化顺序。保留 Desktop shell 能力检测、标签附着与原生文件操作，Host 浏览器继续使用浏览器对应路径。

**完成条件**　主仓 full、headless 和打包桌面三条入口均在无 Docker 的环境完成启动和主要操作。CLI/Quick Chat、权限、工作区首屏、历史附件和模型选择通过。两种入口可独立导入、路由装配结果可以审查。**先通过这一阶段，再删除容器执行模块。**

### 阶段 3 · 删掉主仓的 Docker、API 用户和 Android 分支

- 先处理导入和调用方，再移除镜像及容器专属实现。按文件读写和元数据、前台命令、后台命令、持久终端、子智能体资源、工作区记忆与提示词逐链验证，然后清理 `container_file_proxy`、容器监控、Docker 只读与作用域执行器、容器记忆挂载、镜像目录及专属配置。`modules/linux_sandbox/`、Windows WSL 安装脚本及 macOS Host 沙箱继续进入对应安装和打包链。
- 移出 `UserManager` 的多用户职责、`ApiUserManager`、API Token 认证和配额、用户／容器管理界面、`/api/projects*` 及 API 用户路由。先检查 `UserWorkspace` 等共用表示、Host 策略、自定义工具、MCP、提供商、上传和附件路由的调用方。API 用户的管理和执行入口移除后，再收拢相关 `RuntimeIdentity` / `TrustedPrincipal` 分支、部署配置和数据路径引用。Host 对话费用账本、订阅额度和个人设置沿用各自的数据源。
- 在 Host 前后端去掉 Android 专用桥接和 APK 端点、构建和静态入口。保留浏览器的下载、上传、预览和窄屏布局。复核 Vite 入口与 manifest、桌面 staging 和官网桌面更新。
- 清理安装向导中的 Docker 模式选项、容器配额和镜像参数，更新主仓 README、示例配置、项目契约、测试和发布说明。执行侧的产品依赖必须消失。用户项目将 Docker 用作普通命令的能力、历史里的容器路径和历史兼容标识按各自语义处理。

**完成条件**　主仓无 Docker 运行时依赖且没有多用户、API 用户或 APK 的活动路由。`/api/v1/models` 仍可供 Host 消费者使用。fork 具有原账号、API 客户端和 Android 所需接口。旧模式配置有明确提示，Host 沙箱失败仍保持现有拒绝行为。

### 阶段 4 · 切换、观察与回退

- 切换前以部署副本进行一次完整演练。验证应用启动、数据版本、账号和附件可读性、定时任务启动与停止、容器隔离、API 请求及 Android 更新。记录实测结果，保留可启动的上个服务版本和已验证的备份。
- 在演练记录中固定旧服务版本、备份范围、数据格式、恢复位置和实际启停及恢复命令。数据库使用一致快照，工作区文件、记忆和上传保留目录与权限，记录数量和校验信息。回退负责人在副本上执行实际恢复，核对切换后新增数据能否被旧服务识别或迁回，再确认可用的回退路径。
- 正式切换时，先停止受理写入及新任务，核对运行中任务和计划，完结或按现有机制停止。停掉旧写入者后取得最终一致快照，再启动 fork 并切换入口。旧和新服务的计划调度器避免同时对同一批任务发起执行。观察身份、任务、文件、容器及发布错误，确认数据增量可追踪后再结束观察。
- 切换前或 fork 接受写入前发现阻断，恢复旧入口和已验证的旧服务。fork 已接受写入后出现阻断，先停新写入并保存新数据。数据格式兼容时，在副本验证旧服务可读取切换后的数据，再用该数据恢复旧入口。若已发生 schema 变更，先验证逆向迁移并核对切换后产生的会话、任务记录、计划和上传文件。旧快照保留作基线备份，回退前先保全新增数据。
- 主仓阶段可独立回退对应提交或桌面包。回退复用原 Host 数据和兼容接口，再核验会话、审批、标签、定时任务和用量。拆分优先保持现存格式及目录，降低本机回退的成本。

**通过线**　无身份串用、工作区串路或隔离降级，登录与关键工具可用，既有数据可找回，且无重复调度。出现任一项异常、缺失可恢复备份或无法对账时，暂停继续切换。

## 4. 数据归属与兼容

| 数据 | 处理方式 |
| --- | --- |
| 主仓 Host 数据 | 保留 `DATA_DIR` 默认布局、目录覆盖优先级和桌面现有数据根。整体考虑工作区 catalog、Agent/Chat 对话、媒体和附件、定时任务数据库、桌面标签、费用账本、私有记忆、审批配置、Host 密码和 Gateway Token。Host 的多个工作区共用部分存储，沿用现有对话归属。 |
| Docker/Web 部署数据 | fork 接管普通账号及其工作区、租户策略、邀请状态、API 用户与 Token 元数据、工作区数据与上传、容器记忆和定时任务。使用实际生效的数据根、目录覆盖和部署配置，对目录和账号归属逐项核验。生产接手时保留稳定工作区标识，避免附件和任务引用断开。 |
| 历史双源账号 | 当前 Host 可读取 `web/data/users.json`，保存时只写当前 `users.json`，因此 Host 与 Web 的同名记录可能有分歧。交接前做只读差异报告，至少覆盖身份、权限和默认工作区；凭证相关字段只比对一致性。按部署记录确定权威数据，冲突项人工确认，保持原始副本。 |
| 旧 Web 历史迁入 Host | 建议默认让旧账号和原工作区继续留在 fork。有迁入 Host 需求时，使用显式导出和导入，或另行定义离线迁移范围。对话包只携带契约列明的材料，项目源码、普通附件、定时任务、工具配置、记忆等各自验收。按目标重新验证工作区及权限，保留历史消息和路径的原文。 |
| 冻结提示词和历史状态 | 保持旧对话冻结快照，新的环境描述在项目规定的新建或压缩边界生效。既有 Host 子智能体的工作区身份和固定权限继续按原约束恢复。历史 Docker 环境记录可阅读，迁入 Host 的数据不恢复原容器会话或跨环境执行待办操作。 |

参考 [运行态路径](agents_details/runtime_data_paths.md)、[对话迁移](conversation_transfer.md)、[项目记忆](workspace_memory.md) 和 [系统提示词快照](system_prompt_snapshot.md)。Host 旧记忆迁移按 Host catalog 跑；历史 Web 工作区的双读兼容与独立迁移分别验收。

## 6. 实施前需要落定的交付参数

- Docker fork 的仓库位置、访问级别与维护者，实际切换的部署、入口域名及 APK 发布所有者。若 fork 要公开发布源码，单独配置发布 remote、分支与文档保留规则。
- 是否需要在首个版本提供旧 Web 历史迁入 Host 的流程。默认方案只承诺原部署随 fork 延续，保留现有导入能力和独立迁移选项。
- 生产切换窗口、证据记录人和回退负责人。代码审查、分支、提交、推送与对外发布按各自实际授权执行。
