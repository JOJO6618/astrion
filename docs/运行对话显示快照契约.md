# 运行中对话显示快照契约

实现与验证日期：2026-10-08。适用范围：Web/Electron 共用的对话显示加载、主任务事件续接、通知接力、压缩与工作区导航。本文描述当前实现；调查时旧链路与六组竞态见 `2026-10-07_运行中对话加载调查.md`。

## 1. 数据来源与加载顺序

加载运行中的对话仍然使用磁盘与内存两种来源，但由服务端生成一个一致的显示快照：

- **已提交前缀**：任务开始绑定资源时，从对话持久化文件读取并冻结，保存为 `TaskRecord.display_base`。
- **当前任务显示**：`RuntimeProjection` 随任务事件增量维护用户输入、思考、正文、工具、系统通知与交互状态。它保存显示结果，不保存完整事件日志，也不替代模型上下文。
- **续接游标**：快照返回 `next_event_idx`，表示此快照已经涵盖的事件之后，前端应开始读取的位置。

```text
任务事件发布 → 更新显示投影 + 写入有限事件 deque
                         ↓ 同一显示事务捕获
                 历史前缀 + 当前投影 + 游标
                         ↓ bootstrap
               前端离线转换 → 一次提交消息列表
                         ↓ attachSnapshot
               只消费游标之后的增量事件
```

首次加载仍读取完整历史前缀；本轮没有引入历史分页。活动期间的文本片段来自内存投影，不要求每个 token 落盘。进程重启后，运行中投影不存在，只能从已经持久化的历史恢复；本文不承诺恢复未持久化片段。

## 2. 服务端快照与事件契约

唯一显示加载端点为 `GET /api/conversations/<conversation_id>/bootstrap`。关键响应结构如下：

```json
{
  "messages": ["原始已提交历史消息"],
  "display": {
    "revision": "显示版本",
    "messages": ["前端 UI 结构的当前任务消息"],
    "state": {"streaming": true},
    "task": {"task_id": "...", "status": "running"},
    "next_event_idx": 257
  }
}
```

上面的字符串是结构说明，不是实际消息格式。响应还包含模型/模式等 `meta`、主任务与后台活动 `running`、输入队列、压缩状态和文件/预览面板数据。

`server/conversation_view/snapshots.py` 的 `VIEW_LOCK` 是显示事务边界。任务登记、事件发布、显示捕获与终态提交经此边界串行执行。显示、主任务摘要与绝对游标来自同次捕获。后台管理器、工作流等辅助状态沿用各自查询，不应被描述为所有子系统共用一个原子事务。

`GET /api/tasks/<task_id>` 的事件窗口同次返回 `events`、`window_start`、`next_offset`、`status`、`updated_at`。事件 deque 是有限的增量缓存；前端游标落在窗口起点之前时，停止消费该批数据并重新请求统一显示快照。禁止把截断的 deque 当作全部运行显示。

锁顺序保持显示锁在任务记录锁之前；不要在任务记录锁内反向获取显示锁。持久化操作完成并释放目录锁后，再发布需要显示锁的完成事件。

## 3. 生命周期与边界转换

- **开始任务**：冻结磁盘已提交前缀，当前输入及后续输出进入显示投影。前置通知由生产者提供明确 `message_id`，从前缀中移出后由当前投影提供一次。
- **资源尚未绑定**：新任务已经登记但还没有显示前缀时，快照保留前一任务的完整显示，游标归属于新任务。
- **运行任务部分落盘**：快照不把新落盘正文再拼接到投影。持久化消息只按 `message_id` 回填已提交 metadata/媒体字段。
- **完成、停止、失败**：终态和最终投影在显示事务内提交。保留最近任务的完整显示，避免任务刚结束时加载退回较旧磁盘进度。
- **下一任务绑定**：重新冻结已提交前缀，释放同用户/工作区/对话旧任务的完整显示前缀、投影及 context 引用，防止每轮保留一份完整历史。
- **压缩提交**：从已提交历史重建前缀，更新显示 revision；前端收到压缩完成事件后重新接管统一快照。
- **检查点回溯**：按用户、工作区和对话精确退役旧显示记录，再同步回溯后的历史。
- **后台接力**：前台完成但后台子智能体、命令或多智能体仍有活动时，保留活动显示；通知创建后续主任务，再通过统一快照接管。

## 4. 前端写入权

`conversation/bootstrap.ts` 负责显示快照的唯一加载和提交；`conversation/session.ts` 负责导航身份。

每次进入建立新的 `ConversationSession`，每次进入/离开推进视图 epoch。旧请求即使未能及时 abort，仍需在 JSON 解析之后、状态写入之前检查对象身份。A→B→A 和空页面→对话→空页面都不能只靠字符串 ID 判断归属。

历史转换在脱离当前视图的对象中完成，与当前任务消息合并后一次赋值给 `messages`。滚动、工作流和辅助面板请求不阻塞快照提交或事件订阅。

`task.ts` / `taskPolling.ts` 另维护轮询 generation 和 request owner。重新接管相同 task ID 后，旧成功、404、异常、finally 和定时回调都不能推进新游标、停止新轮询或清理新请求。`attachSnapshot` 必须接收归属于当前视图的事件 handler。

对话内辅助 HTTP 请求使用 `auxiliaryOwnership.ts` 的同一视图 epoch 和分类请求序号。实时 todo/token 更新、问题/计划处理完成及详情关闭，会失效同类在途旧请求；旧响应和旧 finally 不得覆盖较新的实时状态。

跨对话的 `/api/tasks` 索引使用页面级请求身份，不绑定导航 session；切换视图不使结果失效。请求失败保留缓存并续排刷新，只有最新请求可提交和续排，页面卸载取消所有索引请求与 timer。发送被运行态缓存拦截前先核实最新索引，不重载历史，也不把请求失败当作空闲。

标题属于对话元信息：事件、快照和补查共用 store 更新入口，覆盖各类型列表、工作区分组、搜索、任务与标签栏。轻量 `/api/conversations/<id>/metadata?workspace_id=...` 只返回该对话的标题和锁定状态，不改变后端当前对话、不提交显示快照；其前端响应与重试 timer 仍检查导航 session 和请求身份。

## 5. 消息与动作身份

- 用户消息由生产者分配 `message_id`，事件与持久化共享。乐观输入回显绑定此 ID；相同文本、不同 ID 是两条消息。
- 当前任务 assistant 与动作使用任务/事件身份，例如 `${taskId}:${eventIdx}:assistant` 和 `${taskId}:${eventIdx}:tool`。
- 工具 preparing、execution、tool call 等别名在快照 hydrate 时一次登记，增量更新命中原动作。
- 历史消息保留持久化 ID；没有 ID 的遗留历史仅在转换时使用稳定索引身份。
- 模型重试按明确 `streamAttemptStart` 动作区间重置，不从尾部工具或文本推测边界。
- 用户时间统一转换为 ISO：Unix 秒/毫秒转换，已有字符串保留。动作时间使用前端毫秒单位。
- 系统通知快照与实时事件沿用相同显示过滤与本地化规则。

## 6. 持久化读写边界

`ConversationManager.read_conversation` / 兼容入口 `load_conversation` 只读取文件，在返回数据中补必要字段，不因加载执行迁移回写或更新索引。

同一持久化目录的多个 manager 共享 RLock。保存及相关读改写事务覆盖读取、按消息身份合并、文件保存和索引更新。目录锁解决同进程多 manager 的互斥；它不是跨进程数据库事务，也没有改变桌面端后端单实例约束。

不要把整个 bootstrap 所有辅助能力概括为绝对无写入：预览 token、资源装配等有各自已有业务生命周期。

## 7. 已删除的恢复机制

- `restoreTaskState`、尾部角色/工具状态判断、运行区间倒推和从事件 0 恢复重放。
- mounted、watcher、初始化和运行任务入口中的第二次恢复。
- bootstrap 下发完整事件后再次下载同一批事件。
- 文本匹配乐观输入、按工具名匹配结果、工具全历史扫描补注册。
- 对账独立清消息、清事件 Set、归零游标或直接接管旧恢复接口。
- 旧 replay 标记、全局 task event handler 后备入口，以及没有消费者的 store 恢复接口。

新任务从游标 0 接收它自己的事件仍是正常发送路径；禁止的是加载既有运行状态时从 0 重建显示。

## 9. 思考内容摘要（2026-10-29）

Chat Completions 的辅助思考摘要通过 `thinking_summary` 事件增量写入显示投影，以 response message ID、generation 和 revision 定位；不得改变当前工具／正文状态。独立存储在实际对话目录下 `thinking_summaries/<id>.json`，每次发布前原子保存。bootstrap 仅在返回的显示副本装配 `thinking_summary`／`thinkingSummary`，不写模型历史或 reasoning_content，不新增恢复旁路。主模型为 Responses 时跳过辅助摘要。

默认关闭且必须显式选择模型，无自动选择；首次3秒且200字符，后续默认20秒且新增500字符。间隔可在设置调整，每次仅发送待总结新增思考末尾最多2000字符，不截断原始思考显示。正常完成事件前等待该工作段摘要收尾以避免轮询终止后丢失更新，正文和工具流不等待请求。详见 `docs/thinking_summaries.md`。本次执行语法检查与用户要求的前端构建，未执行功能或视觉回归，不沿用上节旧结果为新增摘要背书。
